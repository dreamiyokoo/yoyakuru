# 音声・予約アーキテクチャ検討

> 最新の要件は [要件定義 v0.1](requirements.md) を参照してください。本資料は初期検討の記録です。チャット別料金・旧月額など過去の価格は現行方針ではありません。基本機能コミコミ月額1,980円が目標で、番号包含・通話単価などは未確定です。

整理日：2026年11月4日／採用製品と実装は未確定

## 第一候補

電話事業者が着信をOpenAIの音声会話APIへ接続し、AIがヨヤクルの予約APIを呼び出す。ChatGPTアプリを電話番にする構成ではなく、組み込み用のAPIを利用する。アプリと同一の声・品質を保証するものではない。

| 要素 | 役割 |
|---|---|
| 電話事業者 | 番号、着信、SIP接続または音声中継 |
| OpenAI音声API | 音声の理解と応答、予約ツールの呼び出し |
| ヨヤクル | テナント識別、権限、予約ルール、空き枠、確定処理 |
| Google Calendar | 予定の表示、外部の予定との同期 |
| Stripe | 店舗のSaaS利用料の継続課金 |

Direct SIPまたはサーバー音声中継を比較する。直接接続にはOpenAI側の利用可否・電話事業者の対応条件を確認する。現行のモデル名・イベント名は実装開始時の公式仕様で確定する。

## 予約確定

1. AIが日時、メニュー、氏名、連絡先を聞く。
2. サーバーが営業日・所要時間・資源・外部予定を確認する。
3. 有効期限付きで予約枠を仮押さえする。
4. AIが具体的な日付と内容を復唱し、了承を得る。
5. サーバーが再確認し、DBトランザクションで確定する。
6. 成功結果を受け取った場合のみAIが確定を案内する。
7. カレンダー反映・通知を実行し、失敗時には再処理する。

ツール呼び出しやWebhookの再送で予約が増えないよう冪等性を確保する。複数着信は会話ごとに独立セッションとし、番号数と同時通話数を分けて設計する。

## テナントと番号

店舗専用番号とテナントを対応付ける案。既存番号を残す場合は専用番号への転送を検討する。転送元の回線にも同時転送数の制約がある。同時通話の実上限は電話・AI・サーバー各層で検証し、無制限とは約束しない。

番号取得・最終利用者の確認・再販条件は電話事業者に確認する。契約主体と番号の解約・移行時の扱いも決める。

## カレンダー同期

予約情報の正本はヨヤクルDBとし、Google側の一般予定を予約不可として取り込む案。Googleで予約を直接編集した場合の取消・時刻変更の意味を定義する。変更通知と差分取得、監視更新、定期的な照合を設計する。Google側の同時編集まで含む原子的な予約ロックはできない前提で、競合を検出する。

## 失敗時の対応

聞き取り不能・例外相談は折り返し受付。切断時には仮押さえと確定済みを区別する。サービス障害時には従来受付へ戻せるようにし、転送ループを防ぐ。認証情報・通話記録・顧客情報のアクセスはテナント境界で分離する。
